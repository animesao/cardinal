# AGENTS.md — cardinal

This is the entry point for AI agents and new maintainers. It is a map, not an
encyclopedia. Read only what the task needs, then verify against code and tests.

## First 10 minutes

1. `git status --short --branch` and `git log -5 --oneline` — never overwrite
   work you did not create.
2. Read this file, then [`docs/ai/context-map.md`](docs/ai/context-map.md).
3. Read the nearest local `AGENTS.md` for the area you will edit.
4. Read the one relevant architecture document, not all of them.
5. Check [`docs/status/known-issues.md`](docs/status/known-issues.md) before
   trusting older docs.
6. Open the smallest set of source files that can prove or disprove the task.

## What this repository is

`cardinal` is a daemonless Linux container runtime written in Go. It pulls OCI
images, runs containers with namespaces + overlayfs + cgroups, provides a
Docker-compatible HTTP subset, and adds compose-style `up/down`, clusters,
services, FaaS, backups, and blueprints.

Facts to keep in mind:

- Runtime code is Linux-only. Most Go files carry `//go:build linux`; a Windows
  or macOS checkout is for editing and cross-compilation, not for running
  containers.
- The project ships one static binary. `cardinal serve` and
  `cardinal supervisor` are optional long-running components; there is no
  mandatory daemon.
- The root `VERSION` file is the release source of truth. Version markers in
  Markdown are generated by `scripts/sync-docs-version.sh`.
- The filesystem state directory (`CARDINAL_DATA_DIR`) is the source of truth
  for containers, images, networks, backups, clusters, services, and functions.
  There is no database. Without the env var (an empty or whitespace-only value
  counts as unset), uid 0 uses `/root/.cardinal`; other users use
  `$HOME/.cardinal` (falling back to `/root` if the home lookup fails). See
  `internal/state/state.go`.
- The CLI has two layers: a cobra command registry in `cmd/cobra_commands.go`
  and legacy `func Command(args []string)` handlers. Both must stay in sync.

## Source-of-truth order

When documents disagree, trust this order:

1. Runtime behavior: code and tests.
2. Public contracts: `internal/api/types.go`, route handlers,
   `internal/client`, persisted JSON fields.
3. Build and release: `go.mod`, `Makefile`, `.github/workflows/*.yml`,
   `scripts/*.sh`.
4. Generated version data: `VERSION` + `scripts/sync-docs-version.sh`.
5. Maintainer docs (`README.md`, `docs/`, `SECURITY.md`).
6. Plans in `docs/plans/` — historical intent, not proof of current behavior.

If you find drift, record it in `docs/status/known-issues.md`; do not silently
"fix" history or invent a rationale.

## Non-negotiables

- Do not weaken a security control to make a test or demo pass. In particular:
  default seccomp, `no_new_privs`, capability dropping, bind-mount blocklists,
  API bearer-token enforcement, cluster token checks, and archive path checks.
- Custom seccomp profiles are rejected at container start rather than silently
  ignored, and any requested AppArmor profile is rejected. The default seccomp
  profile is applied during container init. AppArmor confinement is not applied.
  Verify the current code before repeating any older claim.
- Do not change persisted JSON field names, Docker-compatible response fields,
  or 204/304 semantics without checking `internal/client`, the panel/wings
  integrations, and both language docs.
- Do not hand-edit the text between version-marker comments; run
  `sh scripts/sync-docs-version.sh` instead.
- Never commit secrets, tokens, `.env` files, private keys, or generated
  binaries.
- Do not run `git reset --hard`, `git clean`, force-push, or delete branches
  without explicit user permission.
- Do not claim a test, lint, audit, or e2e passed unless you ran it and saw the
  result. On Windows, cross-compilation is not runtime verification.

## Verification matrix

Run the narrowest check that can falsify your change, then the repository gates.

| Change | Minimum verification |
|---|---|
| Go code | `gofmt -l <changed files>`, `go test ./... -count=1` on Linux, `go vet ./...` |
| Cross-platform edit on Windows | `$env:GOOS='linux'; $env:GOARCH='amd64'; go build ./...` and `go vet ./...` |
| CLI command/flag | Above + `go test ./cmd/...` on Linux + `cardinal <cmd> --help` on Linux |
| API/remote | `go test ./internal/api/... ./internal/client/... ./cmd/...` on Linux |
| Runtime/security | Linux e2e (`go test`, privileged smoke, or `.github/workflows/e2e.yml`) — compile-only is not enough |
| Docs only | `sh scripts/sync-docs-version.sh --check`, `python3 scripts/check-docs-links.py`, `sh scripts/audit.sh` |
| CI/release scripts | `sh -n` on changed shell scripts if available, plus the relevant workflow dry run |

Repository-wide gates from [`CONTRIBUTING.md`](CONTRIBUTING.md) and `Makefile`:

```sh
gofmt -w $(git ls-files '*.go')
go test ./... -count=1
go vet ./...
golangci-lint run ./...
sh scripts/audit.sh
sh scripts/sync-docs-version.sh --check
python3 scripts/check-docs-links.py
```

On a Windows host without `bash`/WSL, run the POSIX scripts with `sh` when it is
available, use PowerShell for environment variables, and state explicitly which
Linux-only checks were not executed.

## Fact status labels

Use these labels in plans, status files, and handoffs:

- `Implemented` — code exists and a test or runtime check proves it.
- `Partial` — code exists but a known gap remains.
- `Planned` — accepted intent, no working implementation.
- `Deprecated` — still present but should not be used for new work.
- `Unknown` — not verified; say so instead of guessing.

Every non-obvious claim should point to a file, test, command, or commit.

## Change protocol

1. State the goal, scope, and non-goals in a task file for multi-step work.
2. Make the smallest change that satisfies the goal.
3. Update tests with behavior changes; update both language mirrors for
   user-facing docs.
4. Update the relevant architecture doc or ADR only if a durable decision
   changed.
5. Add or close an entry in `docs/status/known-issues.md` when you discover or
   fix drift.
6. Write a handoff with exact commands and results, including failures.

## Context maintenance

Add a new architecture document only when a subsystem cannot be understood from
an existing one. Add an ADR only for a durable, cross-cutting decision. Add a
local `AGENTS.md` only where a future agent would otherwise repeat a costly
mistake. Keep this file short; move detail down the tree.
